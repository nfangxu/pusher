# Fan-out 遍历耗时理论分析

## 分析基础

**代码路径（全量广播 `*`）：**

```
POST /push → PushQueue.Push() → worker goroutine → process()
  → GetAll()           // 遍历 32 个 shard，每个 RLock 后拷贝连接指针
  → for each conn:
      seen[UserKey]    // map 查重
      IsClosed()       // channel select，O(1)
      send()
        json.Compact() // 压缩消息体
        fmt.Sprintf()  // 拼接 SSE 数据行
        conn.Write()   // TCP 写入 syscall
        Flush()        // HTTP flush syscall
```

**关键约束：** fan-out 在单个 worker goroutine 中顺序执行，总耗时 = 连接数 × 单连接耗时。

---

## 单连接操作耗时估算

| 操作 | 耗时估算 | 说明 |
|------|----------|------|
| `json.Compact` | 1–3 μs | 100 字节消息体，纯内存操作 |
| `fmt.Sprintf` | 1–3 μs | 4 个字段替换，内存分配 |
| `conn.Write` | 3–10 μs | TCP syscall，内核缓冲区写入 |
| `Flush` | 3–10 μs | HTTP flush syscall，触发 TCP 发送 |
| `seen` map 查重 | 0.1–0.5 μs | map 查找，O(1) |
| **合计** | **10–30 μs** | — |

取中位数 **~20 μs/连接** 作为估算基准。

## 不同连接数的 Fan-out 耗时估算

| 在线连接数 | GetAll 遍历 | Fan-out 总耗时 | 等效 QPS 上限 | 实测参考值 |
|-----------|------------|---------------|--------------|-----------|
| 100 | ~50 μs | **2 ms** | 500 | — |
| 500 | ~100 μs | **10 ms** | 100 | — |
| 1,000 | ~200 μs | **20 ms** | 50 | — |
| 2,000 | ~400 μs | **40 ms** | 25 | 实测 77ms (P50=65ms) |
| 5,000 | ~1 ms | **100 ms** | 10 | 实测 298ms (P50=293ms) |
| 10,000 | ~2 ms | **200 ms** | 5 | 实测 364ms (P50=340ms) |
| 20,000 | ~4 ms | **400 ms** | 2.5 | — |
| 50,000 | ~10 ms | **1 s** | 1 | — |
| 100,000 | ~20 ms | **2 s** | 0.5 | — |

> **GetAll 遍历：** 32 shard RLock + 遍历 byUser map + 拷贝指针切片，约 0.2 μs/连接。
>
> **实测值 vs 理论值：** 实测约为理论值的 2–3 倍，差异来自 GC 压力、TCP 缓冲区竞争、系统调度开销。

## 瓶颈分析

### 1. 顺序写入（主要瓶颈）

当前 `send()` 对每个连接顺序执行 Write + Flush。N 个连接的网络 I/O 串行化。

**优化方案：** 并发 fan-out，将连接分批，多 goroutine 并行写入。

```
理论效果（假设 4 并发）：
- 10,000 连接：200ms / 4 = 50ms
- 50,000 连接：1s / 4 = 250ms
```

### 2. GetAll() 内存拷贝

`GetAll()` 每次推送都遍历全部 shard 并拷贝连接指针切片。在高频推送下产生大量临时对象，增加 GC 压力。

**优化方案：** 缓存连接快照，仅在连接变更时更新。

### 3. 单 Worker 串行消费

默认 `worker_num=8`，但单次推送的 fan-out 由一个 worker 独占。高 QPS 推送时，后续请求排队等待。

**优化方案：** 将 fan-out 从 worker 中剥离，worker 只负责入队，fan-out 由独立 goroutine pool 执行。

## 容量规划参考

| 场景 | 连接数 | 推送频率 | 延迟预期 | 是否可行 |
|------|--------|---------|---------|---------|
| IM 单聊 | 1 | 任意 | < 1ms | 无压力 |
| 群聊 (小群) | 100 | 10 QPS | ~2ms | 无压力 |
| 群聊 (大群) | 5,000 | 1 QPS | ~100ms | 可接受 |
| 全站通知 | 10,000 | 0.1 QPS | ~200ms | 可接受 |
| 全站广播 | 50,000 | 0.01 QPS | ~1s | 需优化 |
| 海量广播 | 100,000+ | — | ~2s+ | 必须异步 fan-out |

---

## 结论

- 当前架构支持 **万级连接** 的全量广播，P99 < 1s
- 单用户 / Channel 推送（fan-out 范围小）延迟始终在 **毫秒级**
- 瓶颈在顺序 Write+Flush，优化方向为**并发 fan-out**
- 如需支持 5 万+ 连接的实时广播，建议实现分批并行发送
